=====================================================================
 STEPS 2  —  HANDHELD AXIS TEST  (OpenVINS VPS, Jetson "vajra")
 Final working procedure, last updated 2026-09-06
=====================================================================

This is the Stage-1 "axis check": hold the camera still, then translate it
along each axis in turn, and confirm the position estimate moves the same
way. It is the direct regression test for the camera-IMU calibration.

The Jetson is reachable at:  ssh vajra@192.168.55.1   (password: ask the team)

---------------------------------------------------------------------
 0.  ONE-TIME / PER-BOOT SETUP
---------------------------------------------------------------------

Power mode (only needs doing once — it persists across reboots):
    sudo nvpmodel -m 2            # 2 = MAXN_SUPER  (NOT -m 0, that is the 15W throttled mode)

Every boot, before testing:
    sudo jetson_clocks           # lock CPU/GPU to max, disable frequency scaling
    sudo systemctl stop packagekit ; pkill -f update-manager   # stop apt eating CPU

Wi-Fi:
    wifi-mode status             # check
    sudo wifi-mode internet      # dev/analysis (joins "TU")
    sudo wifi-mode flight        # broadcast MOTHER_DRONE AP for a ground station
    (either mode is fine for this bench test)

Clock: fixed permanently — it auto-syncs when online and has an offline
backstop, so bag folders will no longer be stamped 19700101.

---------------------------------------------------------------------
 1.  OPEN THREE TERMINALS ON THE JETSON
---------------------------------------------------------------------

Paste this header block into EACH of the three terminals first:

    source /opt/ros/humble/setup.bash
    source ~/ros2_ws/install/setup.bash
    export ROS_LOCALHOST_ONLY=1

  >>> The  export ROS_LOCALHOST_ONLY=1  line is MANDATORY in all three. <<<
  Without it, on this Jetson the programs cannot see each other and the
  recorder captures nothing. This wasted hours once — do not skip it.

TERMINAL 1  — camera driver:
    ros2 launch vps_uav_benchmarking gemini335l_vio.launch.py
  Wait ~10 s for "startDevice" / streams to settle. Leave it running.
  (If it errors on an unknown Orbbec argument, stop and report it.)

TERMINAL 2  — OpenVINS (the VIO estimator):
    ros2 launch vps_uav_benchmarking openvins_gemini335l.launch.py
  Watch this window. It prints "[init]: ..." lines and will NOT
  initialise until the camera moves. When you see
      [init]: successful initialization
  the filter is live. It then prints periodic lines like:
      q_GtoI = ... | p_IinG = X,Y,Z | dist = D (meters)
  p_IinG is the estimated position, dist is total distance travelled.

TERMINAL 3  — first do the preflight check:
    ros2 run vps_uav_benchmarking check_setup.sh
  Expect [ OK ] on: left IR, right IR (~30 Hz), IMU (~400-500 Hz),
  resolution 848x480, topics present. The "OpenVINS odom" line will
  [WARN] until you move the camera — that is expected.

---------------------------------------------------------------------
 2.  RUN THE TEST  (do it twice)
---------------------------------------------------------------------

PASS 1 — no recording, just watch it track.
  In TERMINAL 3:
    ~/pose_log.sh
  This prints once per second:  t  x  y  z  dist-from-start  (metres).
  Do the handheld motion (section 3). Ctrl-C when done. Paste the output.
  PASS = dist stays under ~1 m, and x/y/z come back toward 0,0,0 each
         time you return to the start mark.

PASS 2 — with recording (only if Pass 1 looked good).
  Re-run  sudo jetson_clocks  first.
  In TERMINAL 3:
    cd ~
    ros2 run vps_uav_benchmarking record_bag.sh axis_test_$(date +%Y%m%d_%H%M%S)
  Do the same handheld motion. Ctrl-C the recorder, then Ctrl-C
  Terminal 2, then Terminal 1.

---------------------------------------------------------------------
 3.  THE HANDHELD MOTION  (~80 seconds)
---------------------------------------------------------------------

SETUP
  - Mark a START SPOT (tape an X on the table). You return to it after
    every axis.
  - Point the camera at a TEXTURED, EVENLY LIT scene — a cluttered desk,
    bookshelf, tools on a wall. NOT a blank wall or ceiling. The IR
    projector is OFF, so the scene must have its own detail.
  - KEEP THE CAMERA POINTED THE SAME WAY THE WHOLE TIME. Do not rotate,
    tilt or pan it. Translation only. Rotating in place breaks the test.
  - Move SLOWLY and SMOOTHLY, about 15 cm/s. No jerks, no fast waves.
  - Bigger moves read cleaner: use 40-50 cm, not 5 cm nudges.

MOTION
  Step  Action                                              Hold
  ----  --------------------------------------------------   ------
   1    Hold DEAD STILL at the start spot                    10 s
   2    Slide ~40-50 cm LEFT, smoothly (~3 s)
   3    Hold still                                            5 s
   4    Slide back to the start spot (right)
   5    Hold still                                            5 s
   6    Slide ~40-50 cm FORWARD (away from you)
   7    Hold still                                            5 s
   8    Slide back to start
   9    Hold still                                            5 s
  10    Lift ~40-50 cm UP
  11    Hold still                                            5 s
  12    Lower back to start
  13    Hold STILL                                           10 s

  - Make step 2 (first LEFT slide) clear and deliberate — that motion
    is what triggers initialisation.
  - If Terminal 2 has not printed "successful initialization" within
    ~20 s, stop, hold still 10 s, then do one firm ~50 cm slide-and-back
    to kick it, and carry on.

---------------------------------------------------------------------
 4.  GET THE RESULTS  (after Pass 2 / after Ctrl-C'ing everything)
---------------------------------------------------------------------

Run this whole block in TERMINAL 3 and send the output:

    source /opt/ros/humble/setup.bash; source ~/ros2_ws/install/setup.bash
    export ROS_LOCALHOST_ONLY=1
    BAG=$(ls -dt ~/axis_test_* | head -1); echo "BAG = $BAG"
    ros2 bag info "$BAG" | grep -E "Duration|poseimu|gyro_accel|image_raw"
    python3 ~/ros2_ws/src/vps_uav_benchmarking/scripts/compute_drift.py "$BAG" 2
    echo "----"
    python3 ~/ros2_ws/src/vps_uav_benchmarking/scripts/flight_analysis.py "$BAG" --odom-topic /ov_msckf/poseimu --plot

  compute_drift.py reads /ov_msckf/poseimu and reports:
    - Start position / End position (should be close to each other)
    - Total path length
    - Endpoint drift  (cm)          <- how far off it ended up
    - Drift as % of path            <- the headline number

WHAT GOOD LOOKS LIKE (handheld, returning to start each axis):
    Endpoint drift    : a few cm to low tens of cm
    Drift as % of path: low single digits  (~1-3 %)
    Z (altitude)      : stays near 0 except during the deliberate UP move.
                        Forward motion must NOT show up as Z motion.

WHAT BAD LOOKS LIKE (what we were fighting):
    Start position already several metres from origin,
    trajectory a smooth ramp of tens of metres, 40-80 % drift.
    -> almost always a live-performance problem: check MAXN_SUPER +
       jetson_clocks, close other programs, or drop the IMU rate.

---------------------------------------------------------------------
 5.  GOTCHAS WE ALREADY HIT (so you don't again)
---------------------------------------------------------------------

  * ROS_LOCALHOST_ONLY=1 missing  -> recorder captures nothing.
  * Jetson in 15W power mode      -> OpenVINS can't keep up live,
                                    diverges. Use MAXN_SUPER (nvpmodel -m 2)
                                    + jetson_clocks.
  * Recording the raw bag is heavy (~2.3 GB / 90 s). If a live run is
    fine WITHOUT recording but diverges WITH it, the disk/CPU cost of
    recording is the cause: record fewer topics or drop IMU to 200 Hz.
  * Leftover OpenVINS processes:  pkill -f run_subscribe_msckf  and
    check with  pgrep  before every run. Stale ones corrupt the output.
  * Analyse a bag FOLDER (the one containing metadata.yaml), not the
    .db3 file inside it.
  * The trajectory is judged by DRIFT %, not by the "[init]: ... 0,N"
    lines or by grepping for update messages — those look alarming
    even on a healthy run.
